# Migration Execution Order for Appointment System

This document explains the order in which migrations should be executed to properly handle the enum type dependencies.

## Proper Execution Order

1. **20250530085000_define_appointment_enums.sql**

   - Defines all enum types needed for appointment functions
   - Creates them idempotently using DO blocks

2. **20250512100000_init_schema.sql**

   - Main schema initialization
   - Will run after the enum types are defined
   - Contains TEXT-based function signatures to avoid dependency issues

3. **20250601000000_fix_appointment_functions.sql**

   - Recreates the appointment functions with proper signatures
   - Uses TEXT parameters but properly casts to enum types internally
   - Ensures functions work correctly with the enum types
   - Fixed `process_appointment_payment` function that had incorrect enum usage:
     - Corrected parameter type from `appointment_method_enum` to `text` for service_type
     - Fixed missing enum type in `payment_status = 'completed'::` statement
     - Added proper casts to enum types throughout the function

4. **20250601000100_update_grants.sql**
   - Updates permissions for the functions with the new signatures

## Issue Background

The original migration had enum types in function signatures before the enum types were created. This caused errors like:

```
ERROR: type appointment_method_enum does not exist (SQLSTATE 42704)
```

Additionally, there were enum-related issues such as:

1. Using incorrect enum types for parameters (e.g., `appointment_method_enum` instead of `appointment_type_enum`)
2. Missing enum type specifications in cast operations (e.g., `'completed'::`)
3. Inconsistent use of enums between function signatures and function bodies

The solution is:

1. Define all enum types first
2. Use TEXT in function signatures
3. Cast to enum types internally
4. Update function signatures after enum types exist

This approach ensures the database can be reset and migrations run in order without errors.
